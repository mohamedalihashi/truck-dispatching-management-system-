4.1 Introduction

This section provides an overview of the GaariHel system’s implementation, testing, and evaluation. It connects the work done in the previous chapters, moving from system design to actual implementation, followed by testing and validation. The purpose of this stage is to ensure that the developed system functions as expected and meets the requirements defined in Chapter III (R1–R15 and NFR1–NFR8).

Implementation was carried out using React for the web client, Node.js and Express for the API, PostgreSQL with Prisma for persistence, and WaafiPay for mobile-money collection. The project repository is organised into frontend/ and backend/ folders with automated tests in This chapter presents screenshots of the system, functional test cases, backend and API testing, and security measures applied in the prototype. Screenshots are taken from the running application pages (admin dashboard through driver and customer screens) and sized for print.

4.3 Backend and API Development & Testing

4.3.1 Backend

The backend is implemented in Node.js with Express. Entry point backend/index.js creates the HTTP server and Socket.io. Routes are grouped by resource: auth, cargo-requests, trips, trucks, users, payments, shared-trips, notifications, support, and admin reports. Business logic resides in repository modules under backend/services/db/ (for example tripRepository, cargoRepository, sharedTripRepository, paymentRepository). Shared helpers cover trip status validation, payment workflow, pricing rates, and Somalia geography.

4.4 Security Implementation and Testing

4.4.1 Authentication and Authorization

Users authenticate with email and password; passwords are stored hashed. Successful login returns a JWT used on subsequent requests. Middleware requireAuth and requireRole protect routes. Administrators alone may assign trucks and pool shared loads. Drivers cannot change fare or ETA on assigned jobs. Customers may pay only their own invoices. Shared drivers cannot create or publish shared routes; assignment is admin-only. JWT expiration and password-change policies reduce session hijack risk.

4.4.2 Input Validation

Server-side validation uses Zod schemas on registration, booking, assignment, and status update payloads. Client-side form validation (React Hook Form) improves usability but is not trusted for security. File uploads (cargo photos, proof of delivery, driver documents) are restricted to authenticated endpoints with size and type checks via Multer. SQL injection is mitigated by Prisma parameterised queries. Secrets (DATABASE_URL, JWT secret, Waafi credentials) are loaded from environment variables, not source code.

4.4.3 Security Testing Methods

Security verification included manual tests: accessing admin routes without admin role (expect 403), attempting payment before Delivered (expect blocked), and submitting malformed JSON (expect 400). Role separation between FTL and SHARED driver routes was tested with DriverServiceGuard on the frontend and matching backend checks. Automated dependency audit (npm audit) was run periodically during development. Formal penetration testing with OWASP ZAP was not fully automated in the prototype phase; known OWASP concerns (broken access control, injection) were addressed through middleware, ORM, and role checks as described above.

4.5 Summary of Implementation Results

GaariHel was successfully implemented as a working prototype covering FTL and SHARED workflows, admin assignment, driver Accept/Reject (including one Accept for shared pools), GPS tracking, fare calculation at Delivered, and WaafiPay payment gating. Functional and automated tests support requirements R1–R15. The screenshots and architecture diagram in this chapter were captured from the running GaariHel prototype. Performance under heavy concurrent load was not formally benchmarked; this is noted as a limitation for Chapter V.
